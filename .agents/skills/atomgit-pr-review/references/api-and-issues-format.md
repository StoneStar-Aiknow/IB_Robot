# CLI 读取与评审评论

## 数据与完整性

`gitcode pr view N -R owner/repo --json` 返回 PR 对象；`--comments` 组合可能返回
`{pull_request, comments}`，不要混用。单独 `pr comments --limit 0 --json` 获取评论。
`gitcode api 'repos/owner/repo/pulls/N/files?page=1&per_page=100'` 原生输出 JSON，
没有 `--json`/`--paginate`。commits 端点同样逐页读取。

逐页检查成功退出和数组结构，再合并确实不同的页，例如 `jq -s 'add' page1.json page2.json`。
文件按 filename、提交按 sha 去重检查，并与 PR 的独立总数比对；重复页不能循环追加。
缺总数或完整性无法证明时明确报告，不能把不完整数据作为审计通过依据。

完整 patch 在 files 记录的 `patch.diff`（也兼容字符串 patch）。`pr diff --json` 只有统计。
源文件从 `head.repo.full_name` 和完整 `head.sha` 指定的仓库/版本读取：
`gitcode api 'repos/SOURCE_OWNER/SOURCE_REPO/contents/PATH?ref=FULL_SHA'`。
路径和 query 需正确 URL 编码；contents 的 base64 内容先解码，不能当源码直接分析。
也可 fetch 已确认源仓库的精确 commit 后本地 `git show SHA:path`，不改变用户工作区。

files 端点的 rename 配对与本地 git 不同：平台可能把「删除旧路径 + 新增新路径」合成一条
`status=renamed` 记录，且实测 `previous_filename` 为空、`changed_files` 计数与本地
`git diff --name-only`（默认）或 `--no-renames` 均不一致（PR460 实测 61 / 62 / 65）。
平台计数只用于平台自洽校验；文件级核对与 Docker 指纹一律以本地确定性 diff 为准，
不据 `previous_filename` 虚构删除文件，也不猜测平台的配对阈值。计数差异不能只引用该
现象放行：逐路径比对并用 base/head 树核对确认差异确为 rename 配对，核对后仍无法解释
的差异按清单不完整处理。

保存目标 owner/repo/PR、源仓库和 SHA，发布前回读核对；同 SHA 不意味着不同源仓库
可以互换。部分文件读取失败时标明覆盖范围，不发布全量通过结论。

## 评论格式

普通 Markdown 文件足够，不再要求 `issues.json` 或调用 Python formatter。
一条发现包含严重性、标题、文件与行号、触发条件、影响和修复建议；必要时加简短代码片段。
严重性可用 🔴 critical / 🟠 error / 🟡 warning / 💡 suggestion。

```markdown
🟠 **具体问题标题**

触发条件与影响，附文件/行号证据。

**修复建议：** 最小改动方向。

---
🤖 generated by ai@<真实模型名>
```

总体摘要以 `## 代码审查摘要` 开头，列出发现、方案对比、验证及未覆盖范围。
不要为凑数量输出无依据问题。架构评论另标 SSOT、契约、包职责、文档或复用维度。

## 发布

遵循 skill 的人类确认和版本核对协议。`pr comment --body-file FILE` 发表 PR 级评论；
加 `--path PATH --position N` 时 N 是当前 new-side 文件行号（与网页 diff 新版行号一致）。
仅允许当前 hunk 可见行；old-side、过时定位或缺文件路径时不猜测、不静默降级。

`pr reply` 只支持 `--body`，复杂正文用安全参数数组传入，不能拼成 shell 命令。
comment/discussion ID 各有用途，以对应 `--help` 为准。**ID 按响应保留原值**：本次观察
到发布响应的 id 与评论列表的 id 类型不同（十六进制与数字），不要互转或假设一一对应；
关联线程用稳定的 `discussion_id`。

**行内评论的回读定位**：本次实测 `pr comments` 回读可能缺 `path`/`position`；缺定位只
说明「定位未知」，不能据此把行内评论断言为 PR 级评论，需定位核验时在网页 UI 确认。
发表后保存发布响应与稳定 `discussion_id` 并做回读；超时/失败后先回读核对，结果未知不能
自动重发；threaded 回复在已测试读回通道不可见时需人工 UI 核对。
修复与线程跟进按 `atomgit-review-resolution` 由 Agent 直接执行，不使用自动恢复账本。
