# AtomGit 评审意见处理

Agent 直接使用官方 `gitcode` 跟进评论，代码修复由 Agent 编辑，提交推送复用
`ibrobot-git-flow`。不再提供项目修复执行器、JSON 修复协议或断点恢复程序。

## 读取与确认

从用户链接确认目标 owner/repo/PR；`origin` 是源 fork，不能自动当作目标。
使用 PATH 上的 `gitcode`（不是 Graphviz `gc`），参数按对应命令 `--help` 查询。
未认证时由用户在私密终端执行 `gitcode auth login --hostname atomgit.com`。

```bash
GC_HOST=atomgit.com gitcode pr view 123 -R openEuler/IB_Robot --json
GC_HOST=atomgit.com gitcode pr comments 123 -R openEuler/IB_Robot --limit 0 --json
```

逐条读原评论，区分 comment ID 与 `discussion_id`，核对作者、正文及 `resolved`。
发布响应与列表的 id 类型可能不同（本次观察到十六进制与数字并存），按各响应保留原值、
不互转；线程关联只用稳定 `discussion_id`。`pr comments` 回读可能缺 `path`/`position`：
缺定位记为「定位未知」，不能据此把行内评论当 PR 级评论处理；需定位核验时在网页确认。
不按用户名规则猜测 bot，也不自动丢弃自己的评论。需要源码时按
[通用评审 skill](../atomgit-pr-review/SKILL.md) 确认源仓库、完整 head SHA 和当前 diff。

## 修复、验证与推送

1. 展示拟处理的发现与修复方向。沿用用户已经明确授权的修复范围；有歧义或不同意意见时
   说明原因，不能为了关闭评论强行改代码。
2. 确认本地分支属于 PR 源仓库且基于当前 head；保留用户已有修改，逐项编辑并做相关测试。
3. 按 `ibrobot-git-flow` 精确暂存、DCO/AI 披露、fixup/autosquash，保持 PR 至多 5 个提交。
   重写前保存源分支远端完整 OID，推送时用绑定该 OID 的 lease，禁止裸 force。
4. 推送成功后回读源分支/PR head，确认等于预期提交，再回复“已修复”。仅本地修改或
   推送失败时如实说明未完成，不关闭线程，也不声称远端已有修复。
5. 更新 PR 描述，覆盖全部 commit 的模型并集和实际验证结果，遵循 `atomgit-pr` 的本地检查。

## 回复与解决线程

先确认回复内容和发布授权。以下编号仅为示例，执行前核对 discussion 确属目标 PR。

```bash
GC_HOST=atomgit.com gitcode pr reply 123 -R openEuler/IB_Robot \
  --discussion DISCUSSION_ID --body '已修复：提交 SHA，验证结果及必要说明。' --no-interactive
# 仅在修复已验证且获得 resolve 授权后，标记行内 discussion
GC_HOST=atomgit.com gitcode pr comment resolve 123 DISCUSSION_ID -R openEuler/IB_Robot --no-interactive
# 需要重新打开时使用 unresolve
GC_HOST=atomgit.com gitcode pr comment unresolve 123 DISCUSSION_ID -R openEuler/IB_Robot --no-interactive
```

`pr reply` 仅支持 `--body`，复杂正文用安全参数数组传入，不拼接为 shell 代码。
要明确发表 PR 级说明时用 `pr comment --body-file FILE`；不能把无法定位的线程回复
悄悄改为顶层评论。行内评论缺文件路径、new-side 行不可证明时停止，不能猜定位。
回复标注实际模型，例如 `🤖 generated by ai@<真实模型名>`。

写后回读核对。已验证的 CLI/API 读取通道可能不返回 threaded 回复，需在网页确认；
超时、非零退出或列表没找到回复不证明未写入，**不能自动重发**。
resolve 后核对 `resolved`；普通 PR 级评论不当作可 resolve 的行内 discussion。

## 中断后继续

重新读取远端 Git head、评论和 resolved 状态，再决定剩余工作。旧修复状态文件和
`pending_push`/`pending_replies` 账本不再受支持，不自动迁移或重放。
无法确定是否已发表的回复先人工核对，保留原状态文件作核对资料，不将其当执行指令。
