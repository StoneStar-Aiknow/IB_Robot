# PI05 Ascend OM Conversion Workflow

Convert a local PI0.5 LeRobot policy into a strict IB-Robot Ascend deployment containing VLM and
Action Expert OM artifacts, compiler ABI metadata, and a named deployment in
`<bundle>/inference_manifest.json`.

Use the repository entry point `python3 -m model_utils.pi05_export`. Do not create a second export
script, hand-edit generated ABI bindings or identities, or deploy raw OM paths outside the policy bundle.

This is an internal workflow reference. `om-convert` is the only user-facing entry point.

## Parent Handoff Contract

Before any PI05-specific question or command, require all of these values from `om-convert`:

| Field | Requirement |
|-------|-------------|
| `model_path` | Absolute existing bundle path |
| `model_type` | Exactly `pi05`, validated from `<model_path>/config.json` |
| `soc_version` | Exact ATC target value, including the full chip revision |
| Host evidence | OS, `npu-smi` result, and ATC version or availability |

If any value is absent, return to the shared resolution steps in `om-convert`. Do not independently
guess or ask again for the model path, model family, or target SoC. If the config changes after
handoff, stop on the mismatch and return to the parent workflow.

## Supported Scope

| Item | Support |
|------|---------|
| Policy | PI0.5 / PI05 only |
| Backend | Ascend ACL OM |
| Standard precision | FP16 VLM + FP16 Action Expert |
| Default NPU text MLP | Accuracy-preserving NPUGeglu |
| Optional acceleration | FastGELU override during NPU ONNX export; may reduce accuracy |
| Optional quantization | Available only through the explicit optional optimization workflow |
| Validation | Strict manifest loading, Torch-vs-ONNX, Torch-vs-OM, and per-OM ais_bench loop 20 |

For RKNN use `rknn-convert`. For Houmo HMM use `hmm-convert`. Return ACT requests to the shared
`om-convert` workflow, which selects the internal ACT reference. Do not route SmolVLA OM requests
through this workflow.

PI05 ONNX export defaults to FP16. Keep demonstrated sensitive islands such as QK/mask/Softmax in
FP32 when required by the validated graph; do not interpret "FP16 ONNX" as an instruction to cast
every operation blindly.

## Mandatory Interaction Gate

Collect all PI05 choices below together with the shared upfront intake in `../SKILL.md`. Do not spread
foreseeable choices across repeated pauses. Do not start export or ATC before the intake is complete.

### 1. Resolve PaliGemma Assets

Include the PaliGemma tokenizer/assets choice in the shared upfront intake. Present:

- `Use a local PaliGemma asset (Recommended for offline/reproducible conversion)`: the user provides
  the path to an existing PaliGemma tokenizer directory.
- `Download automatically`: use the Hugging Face repository identifier already declared in
  `policy_preprocessor.json`, download its tokenizer before conversion, and vendor the resulting files
  into the PI05 bundle.

Be precise about the boundary: `model.safetensors` in the PI05 policy bundle already contains the
trained PaliGemma/VLM weights. The exporter does not accept a separate PaliGemma model checkpoint and
must not combine generic PaliGemma weights with the PI05 checkpoint. This question controls tokenizer
and processor assets only.

For a local choice:

- require the user to provide the path explicitly;
- if it is already inside `model_path`, keep it there;
- if it is outside `model_path`, explain that deployable bundle references cannot escape the bundle
  root and ask for explicit approval to copy/vendor it into a named directory under the bundle;
- inspect the tokenizer processor in `policy_preprocessor.json` and all recognized references named
  `tokenizer_name`, `action_tokenizer_name`, or `paligemma_tokenizer_name`;
- do not copy files or rewrite processor metadata without explicit user approval;
- after an approved vendor operation, set the tokenizer processor's authoritative `tokenizer_name`
  to the new bundle-relative path and update any duplicate recognized references consistently;
- stop if the path is missing or conflicts with processor metadata and the user does not approve the
  required bundle update.

For automatic download, current PI05 exporter subprocesses use local-files-only loading. Therefore
download and vendor the tokenizer before running `pi05_export`; do not rely on conversion or
verification to fetch it lazily:

- inspect and report the exact Hub identifier from `policy_preprocessor.json`;
- require network access and any Hugging Face authentication needed by that repository;
- collect approval for a bundle-local destination in the upfront intake, defaulting to
  `<model_path>/tokenizer`;
- use `transformers.AutoTokenizer.from_pretrained(HUB_ID)` and `save_pretrained(DESTINATION)` to
  download only tokenizer assets through the standard Hugging Face cache;
- update the tokenizer processor and any duplicate recognized references to the destination's
  bundle-relative path;
- do not download a separate PaliGemma model checkpoint or claim that ONNX export does so.

Use the following template only after resolving and quoting all placeholders:

```bash
source .shrc_local
python3 - "RESOLVED_HUB_ID" "RESOLVED_BUNDLE_TOKENIZER_DIR" <<'PY'
import sys

from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained(sys.argv[1])
tokenizer.save_pretrained(sys.argv[2])
PY
```

After either choice, validate `policy_preprocessor.json` with the same production metadata rules used
by the bundle loader:

```bash
source .shrc_local
python3 - "RESOLVED_MODEL_PATH" <<'PY'
import sys
from pathlib import Path

from inference_manifest import load_policy_metadata

metadata = load_policy_metadata(Path(sys.argv[1]), require_native_weights=True)
print(metadata.policy_type)
print(metadata.external_dependencies)
PY
```

Proceed only when the selected tokenizer resolves as a bundle-local asset and no conflicting
recognized references remain. For the automatic-download path, `external_dependencies` must no
longer list the PaliGemma tokenizer Hub identifier.

If processor metadata contains neither a valid bundle-local tokenizer reference nor a Hub identifier,
stop and ask the user to fix the PI05 bundle. Never guess a PaliGemma repository identifier.

### 2. Resolve Pipeline Steps

Include default versus custom steps in the upfront intake. Explain that explicitly selected steps are
rebuilt even when their output already exists.

Present the default as the recommended first option:

- `Default FP16 pipeline (Recommended)`: `vlm_onnx,ae_onnx,verify,vlm_om,ae_om`
- `Custom steps`: the user chooses from the registry below

Explain the step meanings in the intake:

| Step | Meaning |
|------|---------|
| `vlm_onnx` | Export the PI05 vision-language prefix model to ONNX and save VLM-to-AE handoff tensors. |
| `ae_onnx` | Export the Action Expert to ONNX; it consumes handoff tensors produced by `vlm_onnx`. |
| `vlm_om` | Compile the FP16 VLM ONNX to Ascend OM with ATC. |
| `ae_om` | Compile the FP16 Action Expert ONNX to Ascend OM with ATC. |
| `verify` | Compare split ONNX behavior with the source policy; uses the task stored in the required observation batch by default. |

Dependency rules:

- `ae_onnx` needs the `vlm_onnx` handoff tensors, either produced in this run or already present.
- `*_om` needs its matching ONNX product.
- Creating a deployable FP16 bundle for the first time needs both `vlm_om` and `ae_om`. Once the named
  deployment exists, rerunning one OM role inherits the unchanged counterpart artifact and bindings from
  that Manifest deployment; only the rebuilt role needs work-directory OM/ABI files.
- Do not offer quantization as a conversion step. If the user later explicitly selects it, follow
  `optimize.md` with representative real data.
- `verify` is mandatory for a complete conversion and must use the canonical versioned observation
  batch, not generated dummy inputs. The existing verifier uses deterministic seed `42` by default and
  gates on the worst action cosine mean: `>= 0.9999` is `PASS`, `[0.999, 0.9999)` is `MARGINAL` with a
  successful exit, and `< 0.999` fails. Max-abs, mean-L1, KV-cache metrics, and mask equality are
  diagnostic only. Do not pass unimplemented `--verify-*` options or claim that this fixed gate enforces
  user-defined thresholds. The lower-level `convert_om` defaults to `--precision_mode_v2=origin`; use it
  for the conservative baseline. After accuracy passes, an ATC-default candidate may use explicit
  `--precision_mode_v2=fp16` against the same target package. Do not pass the literal value `default` or
  add an unvalidated generic `--atc-arg` path.
- Omit `--task` for the normal canonical-batch workflow. Passing `--task` is an explicit experiment
  override and takes precedence over the task stored in the batch; record that override in the report.

If the user chooses custom steps, collect the exact comma-separated step list and validate the
dependencies before running anything.

### 3. Resolve FastGELU

Include FastGELU in the upfront intake. Present `Disabled (Recommended for accuracy)` first.

Explain the tradeoff:

- Disabled: uses the accuracy-preserving `NPUGeglu` fusion for the Gemma text MLP and is the default
  for NPU export.
- Enabled: exports Ascend `NPUFastGelu`, which can reduce inference latency and improve throughput,
  but it is an approximation and can reduce action accuracy.

Never silently enable FastGELU. When enabled, use `--fast-gelu`; when disabled, omit the flag or use
`--no-fast-gelu`. Record the selection in the saved profile and final report.

### 4. Resolve Denoising Schedule

Include the schedule in the same upfront intake. Explain that new Action Expert OM files predict
velocity and the Ascend backend performs Euler integration using a strict schedule packaged in the
Manifest.

Present these choices:

- `Default uniform schedule (Recommended for a first export)`: omit `--schedule-file`; the exporter
  generates a uniform schedule from `config.num_inference_steps` and packages it with the deployment.
- `Existing custom schedule`: collect the path to an existing strict
  `pi05-denoising-schedule-v1` JSON and pass `--schedule-file`. The saved export profile must record
  `schedule_file` so later OM finalization uses the same schedule.
- `Tune later`: use the default uniform schedule now. Schedule tuning is an explicit algorithmic
  optimization under `optimize.md`, not part of conversion.

Do not offer root `schedule.json` scanning or environment variables. A schedule is either packaged as
the named deployment's `denoising_schedule` artifact or is a transient diagnostic override. The
artifact is non-execution and versioned by the deployment revision; changing it changes the deployment
fingerprint. Existing legacy
deployments whose Action Expert output is `action` and which have no schedule artifact retain their old
behavior.

### 5. Collect Remaining Inputs

After the four mandatory choices, collect or derive:

| Input | Requirement |
|-------|-------------|
| Policy path | Use the absolute `model_path` inherited from `om-convert`; do not ask again. |
| PaliGemma assets | Validated bundle-local tokenizer path and whether it was provided or downloaded automatically. |
| Experiment directory | New or existing directory for `onnx/`, `runtime_save/`, and `om/`. |
| SoC version | Use the exact `soc_version` inherited from `om-convert`; do not replace it with a family-level default. |
| Torch export device | Resolve explicitly: use `npu` when a compatible local Ascend device is available; otherwise use `cpu` for supported ONNX-only work. |
| Deployment name | Named FP deployment written into `inference_manifest.json`, e.g. `ascend_target_fp16`. |
| Profile name | Reusable, descriptive name, e.g. `pi05-target-fp16-npugeglu`. |
| Profile config path | Default `~/.config/model_utils/pi05_export.yaml`, unless the user requests another path. |
| Schedule file | Existing strict schedule selected above, or unset for generated uniform schedule. |
| Task | Required for language-conditioned target generation and ONNX verification. |

The parent router has already inspected `npu-smi info`; include that evidence in the report. If the
toolkit cannot find standard C++ headers, use the installed compiler's actual include directories
rather than hard-coding another machine's paths. A known openEuler 310P environment may require:

```bash
export CPLUS_INCLUDE_PATH=/usr/include/c++/12:/usr/include/c++/12/aarch64-openEuler-linux${CPLUS_INCLUDE_PATH:+:$CPLUS_INCLUDE_PATH}
```

Only set this after confirming those directories exist.

Before selecting any `*_om` step, verify that Python ACL can inspect OM descriptors on a compatible
local NPU. The PI05 exporter uses `write_acl_om_abi()` after ATC. On an Ubuntu cross-conversion host
without a compatible NPU, ONNX-only steps can proceed, but a new deployable OM bundle cannot be
finalized locally. Stop before the long OM conversion unless the user explicitly accepts this partial
result; never synthesize ABI metadata from ONNX.

Before any export, require `model.safetensors` to be a regular file in the PI05 bundle. The current
split loaders can otherwise return a newly initialized model after failing to resolve weights; treat a
missing or unreadable weights file as a hard error instead of exporting random weights.

Keep PI05 vision resize, padding, and risky reshape logic on the host by default. CANN 8.1 RC1 may
lower these ONNX patterns differently from intuitive or ORT behavior. If they must enter the graph,
warn the user and validate preprocessed pixels/masks, VLM handoff tensors, and final action.

## Conversion And Profile Creation

Use one explicit command and save the effective reusable parameters with `--save-as`.

Default FP16 template. Replace every `RESOLVED_*` token with the parent handoff values before running;
never execute placeholder text:

```bash
source .shrc_local
python3 -m model_utils.pi05_export \
    --config ~/.config/model_utils/pi05_export.yaml \
    --policy-path "RESOLVED_MODEL_PATH" \
    --exp-dir /absolute/path/to/pi05_export_run \
    --batch-path "RESOLVED_OBSERVATIONS" \
    --soc-version "RESOLVED_SOC_VERSION" \
    --device "RESOLVED_EXPORT_DEVICE" \
    --dtype fp16 \
    --deployment "RESOLVED_DEPLOYMENT" \
    --steps vlm_onnx,ae_onnx,verify,vlm_om,ae_om \
    --no-fast-gelu \
    --save-as "RESOLVED_PROFILE_NAME"
```

For an existing custom schedule, add:

```text
--schedule-file /absolute/path/to/selected_schedule.json
```

The file must contain exactly `format`, `name`, `algorithm`, `model_output`, and `timesteps`, with
`format: pi05-denoising-schedule-v1`, `algorithm: euler`, `model_output: velocity`, and strictly
decreasing timesteps from `1.0` to `0.0`.

FastGELU example changes only the selection and profile name:

```bash
source .shrc_local
python3 -m model_utils.pi05_export \
    --config ~/.config/model_utils/pi05_export.yaml \
    --policy-path "RESOLVED_MODEL_PATH" \
    --exp-dir /absolute/path/to/pi05_export_run-fastgelu \
    --batch-path "RESOLVED_OBSERVATIONS" \
    --soc-version "RESOLVED_SOC_VERSION" \
    --device "RESOLVED_EXPORT_DEVICE" \
    --dtype fp16 \
    --deployment "RESOLVED_DEPLOYMENT" \
    --steps vlm_onnx,ae_onnx,verify,vlm_om,ae_om \
    --fast-gelu \
    --save-as "RESOLVED_PROFILE_NAME"
```

`--save-as` writes the profile before the long conversion starts. If conversion fails, report that
the profile exists but the bundle deployment may be incomplete; do not claim success.

The exporter treats `steps` as transient and does not persist it in profiles. This prevents a later
profile invocation from unexpectedly rebuilding expensive stages. Therefore, always tell the user
to pass `--steps` again when reusing a profile. In contrast, `schedule_file` is persistent: confirm it
appears in the saved profile whenever a custom schedule was selected. Its absence means the exporter
will generate the default uniform schedule from `config.num_inference_steps`.

After resolving arguments, quote the exact profile location printed by the tool. With the default it
is:

```text
~/.config/model_utils/pi05_export.yaml
```

Tell the user how to inspect and reuse it:

```bash
source .shrc_local
python3 -m model_utils.pi05_export \
    --config ~/.config/model_utils/pi05_export.yaml \
    --list-profiles
```

```bash
source .shrc_local
python3 -m model_utils.pi05_export \
    --config ~/.config/model_utils/pi05_export.yaml \
    --profile "RESOLVED_PROFILE_NAME" \
    --batch-path "RESOLVED_OBSERVATIONS" \
    --steps vlm_onnx,ae_onnx,verify,vlm_om,ae_om
```

CLI flags override profile values. Use this for a new `--exp-dir`, deployment name, explicit task
override, or selected steps without duplicating the whole profile.

## Success Criteria And Bundle Location

Success requires all requested products and, for a complete deployment, both OM roles plus valid ABI
files. The exporter prints the exact artifact paths. Normally:

```text
<exp-dir>/onnx/
<exp-dir>/runtime_save/
<exp-dir>/om/
```

The deployable bundle remains the original `--policy-path`, now updated with:

```text
<policy-path>/inference_manifest.json
<policy-path>/artifacts/ascend/<deployment>/...
```

The `model_path` used by inference is the bundle root (`--policy-path`), not `<exp-dir>/om` and not an
individual `.om` file. The `deployment` is the named deployment supplied during conversion.

At the end, always report:

- Absolute bundle path.
- Exact target `soc_version` and how `om-convert` resolved it.
- Local `npu-smi` and ATC evidence inherited from `om-convert`.
- Named deployment.
- Absolute experiment directory and OM directory.
- VLM and Action Expert OM paths.
- Profile name and profile YAML path.
- PaliGemma tokenizer source: user-provided or automatically downloaded, plus final bundle-local path.
- experience hits-among-evaluated and catalog coverage from `experience-ledger.md`.
- Whether default/custom steps and NPUGeglu/FastGELU were used.
- Schedule name/source/step count and whether `schedule_file` is recorded in the profile.
- Any incomplete role, failed verification, or accuracy warning.

## Accuracy Validation

Generate or reuse targets only from the original Torch deployment on the resolved Torch host. Do not
generate replacement targets from the new OM. Transfer the exact versioned observation batch, targets,
raw targets, and noises according to `multi-host-validation.md`. Compare matching NPUGeglu/FastGELU and
denoising-schedule branches.

Example:

```bash
source .shrc_local
source install/setup.sh
python3 src/model_utils/model_utils/loss_compare.py \
    --config /absolute/path/to/loss_compare.yaml \
    --profile pi05-baseline \
    --policy_path "RESOLVED_MODEL_PATH" \
    --deployment "RESOLVED_DEPLOYMENT"
```

Treat regressions in normalized Raw L1, Raw cosine, W1/std, or first-frame cosine as possible export
or runtime adaptation errors. For Torch vs ONNX, record the fixed action-cosine verdict and all
diagnostic metrics without claiming configurable max-abs or mean-L1 gates. Apply the current
`loss_compare` mean-L1 and cosine limits to Torch vs OM as defined by `accuracy.md`. FastGELU may trade
accuracy for speed, but the tradeoff must be measured rather than assumed.

## Performance Baseline

After collecting the conservative accuracy report, run both VLM and Action Expert OM with
`ais_bench --loop 20` according to `benchmark.md`, even in report-only mode or when a threshold is not
yet accepted. Accuracy acceptance gates optional optimization, not baseline measurement. Report:

```text
total_mean_ms = vlm_mean_ms + action_expert_mean_ms * denoising_steps
```

Also report weighted median and p99 estimates with the required estimate labels. Do not run hardware
mock, LTTng, tracing, or trace summaries.

## Troubleshooting

### Profile was saved but conversion failed

The profile is reusable configuration, not proof of successful compilation. Report the failing step,
retain successful artifacts, fix the cause, and rerun the required `--steps` with `--profile`.

### Deployment is missing after a single OM step

A new split PI05 deployment needs both VLM and Action Expert OM artifacts. Run the missing counterpart
step once to create it. For an existing named deployment, a single-role rerun reuses the counterpart
artifact and bindings from the Manifest and publishes the rebuilt role as a new generation.

### ATC cannot find `cstdint`

Inspect `g++ --version` and the actual C++ include directories. On the verified openEuler GCC 12
environment, exporting `CPLUS_INCLUDE_PATH` to `/usr/include/c++/12` and its platform subdirectory
resolved this. Do not assume those paths on another host.
